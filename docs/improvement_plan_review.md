## Correct the causal language

- **9/100 false alarms is not proof of calibration failure or distribution shift.** The 5% rule was an illustrative empirical normal-tail policy, not a guarantee of test FPR. Under the simplified independent Bernoulli model with true FPR exactly 5%, `P(X >= 9)` for 100 normals is approximately 0.0631. This calculation illustrates finite-sample variability; the estimated threshold and unknown board dependence make this simplified model insufficient for a definitive significance claim. Compare calibration/test score distributions descriptively; report uncertainty and threshold ties. Do not label the threshold defective from the observed count alone.
- **43% recall at one operating point is not representation capacity.** Retrospective recall versus realized FPR quantifies the operating-point tradeoff on these same examples. It does not identify an independently validated replacement threshold or prove all missed defects were recoverable.
- **Mask survival is not visual-detail survival.** The 100 nonempty reduced masks confirm annotation presence, not that scratches/components remain distinguishable in RGB features. A2 size/score association supports a resolution hypothesis, not resize causality. A matched resolution-only ablation is needed.
- **Poor pooled/per-image agreement is a heterogeneity finding.** Pooled pixel AP weights individual pixels and permits cross-image ranking; per-image AP evaluates each image's internal ranking. Report both and defect-area contributions. Calling pooled AP universally “overly optimistic” discards its legitimate pooled estimand; it is insufficient alone for consistent localization.
- **Cross-location matches are not automatically errors.** Similar healthy components may be valid references. Winning patch displacement plus a missed defect is descriptive. A controlled unrestricted-versus-position-restricted comparison and inspectable component context are needed to support a causal explanation.

## Method-source corrections and exact recipe target

The [PatchCore paper](https://arxiv.org/html/2106.08265v2) explicitly links the Amazon implementation; use [amazon-science/patchcore-inspection](https://github.com/amazon-science/patchcore-inspection), pinned to the already researched `fcaa92f124fb1ad74a7acf56726decd4b27cbcad`. [PP-explore/PatchCore](https://github.com/PP-explore/PatchCore) is another implementation, not the authors' reference. The paper's neighborhood-weighted image score and an author-code reproduction are distinct targets; record which one is implemented rather than using “faithful” without qualification.

| Boundary | Correction to implementation plan |
| --- | --- |
| Patch extraction/alignment | [Author patchcore.py](https://github.com/amazon-science/patchcore-inspection/blob/fcaa92f124fb1ad74a7acf56726decd4b27cbcad/src/patchcore/patchcore.py) unfolds each layer into padded 3×3 neighborhoods at stride 1, then bilinearly aligns the lower-resolution patch grid to the first-layer grid with `align_corners=False`. Simple feature-map concatenation alone is not this exact pipeline. Preserve source image, grid and spatial transform identity. |
| Embedding reduction | [Author common.py](https://github.com/amazon-science/patchcore-inspection/blob/fcaa92f124fb1ad74a7acf56726decd4b27cbcad/src/patchcore/common.py) flattens each layer's patch tensor and adaptive-average-pools to a configured pretraining embedding dimension; stacked layers are pooled again to the target dimension. The README example specifies 1024/1024. Set and test both dimensions explicitly. |
| Coreset | [Author sampler.py](https://github.com/amazon-science/patchcore-inspection/blob/fcaa92f124fb1ad74a7acf56726decd4b27cbcad/src/patchcore/sampler.py) reduces dimensionality with an untrained linear projection when necessary; approximate greedy selection defaults to 128 projected dimensions and 10 random initial points, updating minimum anchor distances. It avoids a full N×N matrix but still iterates over selected anchors. Record NumPy/Torch seeds and projection identity. Select indices in projected space but retain original scoring embeddings. A candidate pre-subsample or capped anchor count is an additional approximation. |
| Distances/image score | Author FAISS `IndexFlatL2` returns squared L2; author scorer averages returned neighbor distances and `PatchMaker.score` takes a maximum across patches. With one neighbor this is max nearest squared-L2. The paper describes neighborhood reweighting. Do not silently mix raw Euclidean, squared-L2, multi-neighbor means and paper weighting; thresholds and cross-run raw scores are not interchangeable. |
| Map generation | Author code bilinearly resizes the patch map and applies Gaussian smoothing with sigma 4. Freeze smoothing, output geometry and units. The pilot's unsmoothed Euclidean maps are a disclosed departure. Smoothing is a separate variable for localization comparison. |

[Anomalib's maintained PatchCore documentation](https://anomalib.readthedocs.io/en/latest/markdown/guides/reference/models/image/patchcore.html) supports ResNet18 layer2/layer3 and documents weighted image scores when more neighbors are used, with maximum patch score for one neighbor. It is another supported implementation target, not proof that its preprocessing/reduction equals Amazon source. Include fixtures comparing representative synthetic features and exact algorithm stages before making a reproduction claim.

## Backbone rights and compute risk

Use the precise torchvision model name **`wide_resnet50_2`** and explicit `Wide_ResNet50_2_Weights.IMAGENET1K_V1` or `_V2`; `DEFAULT` currently denotes V2. [Official documentation](https://docs.pytorch.org/vision/0.21/models/generated/torchvision.models.wide_resnet50_2.html) lists 68,883,240 parameters and approximately 11.4 GFLOPs for the classification model at reference input. This is substantially larger than the pilot's ResNet18. These full-backbone figures do not directly predict layer3-truncated CPU latency.

[Torchvision's model-use statement](https://github.com/pytorch/vision/blob/main/README.md#pre-trained-model-license) warns of separate training-dataset-derived model terms. [ImageNet access terms](https://www.image-net.org/download.php) restrict Database use to noncommercial research/education. As recorded for Run 1, local educational evaluation is the present scope; commercial deployment/weight redistribution rights remain unverified. BSD code licensing supplies no separate unrestricted checkpoint grant. Record checkpoint URL/hash, weight version and scope before use.

Sizing example, not a measured allocation: 723 normals at a 512-square input and a layer2 64×64 grid yield 2,961,408 patches. Concatenated WR50 layer2/layer3 channels total 1,536, so storing all float32 embeddings would require about **16.95 GiB**; a 1024-dimensional bank would require **11.30 GiB**, before model/intermediate tensors. A 5% coreset of 1024-dimensional embeddings alone is approximately **0.565 GiB**; nearest search and greedy selection costs remain substantial. Unfolded 3×3 neighborhoods multiply temporary feature volume. These calculations make an unconditional full WR50/512/5–10% run unsuitable as a default on the measured 16GB machine.

Plan a normal-only smoke, streamed/chunked extraction, explicit candidate-bank and final-bank caps, wall-time/RSS limits and projected coreset feasibility before full fitting. If resources force a smaller backbone, candidate pre-sampling or lower resolution, label the departure. A justified smaller recipe is preferable to an out-of-memory attempt; no latency from another GPU transfers to this machine.

## Bounded development study proposed after A2

Freeze a development registry before new runs: maximum **six scored PCB1 configurations**, one normal-only resource smoke per materially different backbone, no broad sweeps, and a proposed per-run stop budget of 8 GiB peak process RSS and 30 minutes elapsed. These are proposed engineering caps requiring adoption before execution, not numerical inspection-success targets. Stopped/debug runs must remain in the registry. If the budget cannot implement a declared recipe, stop and revise the plan openly.

1. Use Run 1 unchanged as the saved comparator. Add a 256 aspect-preserving full-board path and a matched approximately 512 path with the same backbone, score rule and capped memory algorithm. Their contrast addresses effective resolution more directly than replacing everything at once. Persist padding/crop/scale and map reversal; exclude padded background from the correct declared metric geometry.
2. If normal-image geometry shows registration is needed, test one deterministic crop/alignment recipe against its matched unregistered comparator. Verify edge retention, inverse mapping and failures on a score-independent sample. Registration may remove or distort missing-component evidence; it is not guaranteed to help. Identity/no registration is valid when normals are already sufficiently aligned.
3. Compare uniform sampling and approximate greedy coreset at the **same memory count and feature representation**, so coverage versus count is separated. A percentage alone is not a memory budget. Keep the fraction actually achieved and candidate pre-sampling visible. Allocate at most one higher memory-count experiment if resource evidence permits.
4. Allocate one backbone-change configuration only after WR50's normal smoke passes. Treat this as a feature representation contrast; do not simultaneously alter map smoothing, calibration, registration and nearest scoring.
5. Allocate at most one position-aware contrast after alignment is demonstrably usable; select a single radius using PCB1 development rationale rather than a large radius sweep. Define normalized coordinates, empty-neighbor fallback and boundary behavior. It is a **spatial PatchCore extension**, not standard PatchCore. Reuse matched saved embeddings where identities permit.

The order and exact six slots must be instantiated once A2 evidence arrives; the list above is a design framework, not authorization for six slots plus every comparison named. Keep operating-threshold policy normal-only while model/recipe selection may use PCB1 development anomalies transparently. Compare source-coordinate localization or one fixed declared evaluation geometry across resolutions. Never claim higher-resolution gains from metrics evaluated on a different mask grid alone. Freeze improvement-selection criteria and tie-breaking, including per-image localization and runtime, before inspecting new recipe outcomes.

## Optional methods: citations and scope

The [EfficientAD authors' paper](https://arxiv.org/html/2303.14535v3) describes local student–teacher detection plus a global autoencoder for logical anomalies. [rximg/EfficientAD](https://github.com/rximg/EfficientAD) explicitly calls itself unofficial. [nelson1425/EfficientAD](https://github.com/nelson1425/EfficientAD) also explicitly says unofficial; it must not be promoted to an author repository. No author-hosted EfficientAD implementation was verified from the authors' paper or [MVTec's publication listing](https://www.mvtec.com/research-teaching/publications). Cite the paper as primary authority, and independently audit any chosen third-party code/licenses/checkpoints. GPU millisecond results establish no CPU guarantee, and a missing PCB component is not automatically the logical-anomaly task measured on MVTec LOCO.

The handoff's [PaDiM paper](https://arxiv.org/html/2011.08785v1) is correct: it models a multivariate Gaussian at each patch location, retains cross-layer relationships after dimension reduction, and scores with Mahalanobis distance. This makes alignment quality, covariance regularization/sample count and dimension choice important. It is not simply a spatial nearest-neighbor bank. Neither optional method belongs in immediate A2; require a specific unresolved failure hypothesis and a separately bounded comparison later.
